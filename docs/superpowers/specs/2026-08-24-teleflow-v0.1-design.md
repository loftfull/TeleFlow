# TeleFlow Android v0.1 Design

## Goal

Produce a reproducible Android client derived from the official Telegram Android source, branded as TeleFlow, while keeping all product-specific functionality in an isolated extension layer. The first vertical slice must be buildable as an APK and establish stable boundaries for Smart Folders and TeleFlow Drive.

## Product baseline

TeleFlow is an unofficial Telegram-compatible Android client. Telegram messaging, calls, groups, channels, stories, media, contacts, authentication and normal Telegram behavior remain upstream-owned. TeleFlow adds power-user organization and storage capabilities without replacing Telegram's protocol stack.

## Upstream strategy

The build repository is intentionally small. CI checks out a pinned official `DrKLO/Telegram` commit, then applies deterministic TeleFlow transformations. This avoids keeping a many-hundred-megabyte divergent fork and makes upstream rebases auditable.

The build MUST fail closed when an expected upstream anchor changes. Silent fuzzy patching is not allowed.

## Branding and package identity

- Product name: `TeleFlow`
- Android application ID: `com.loftfull.teleflow`
- Beta application ID: `com.loftfull.teleflow.beta`
- Telegram standard name/logo must not be presented as TeleFlow branding.
- TeleFlow remains visibly marked as an unofficial Telegram client.
- The derivative source must remain available under GPL-compatible terms.

## Telegram API credentials

TeleFlow MUST use a user-owned Telegram `api_id` and `api_hash` supplied as CI secrets or local environment variables. The patcher MUST reject missing, malformed, placeholder, or Telegram-official credentials.

Required secret names:

- `TELEGRAM_API_ID`
- `TELEGRAM_API_HASH`

Signing is independent from Telegram API identity. Initial CI may use the upstream dummy keystore only for an explicitly labelled development artifact. A distributable release requires a TeleFlow signing key.

## Extension architecture

TeleFlow additions live under:

`TMessagesProj/src/main/java/org/telegram/teleflow/`

The upstream `org.telegram.*` code should be modified only at narrow integration seams. The extension layer is divided into:

- `core/` — product identity, feature flags, extension lifecycle
- `folders/` — classification rules, preview/apply model, manual overrides
- `drive/` — virtual paths, Telegram-backed object metadata, transfer model
- `automation/` — opt-in IF/THEN rules
- `ai/` — optional classifiers and summarization adapters

No feature may create a second MTProto session inside the app. TeleFlow must reuse the active Telegram account/session and Telegram Android transfer primitives.

## Smart Folders v0.1 boundary

The first domain model is local-only and testable without Telegram networking:

`ChatDescriptor -> FolderRuleEngine -> ClassificationDecision`

Decision inputs initially include chat id, title, username and peer type. Rules are deterministic and ordered. AI classification is not part of the bootstrap APK; an adapter boundary is reserved for it.

The eventual server apply layer will preserve pinned chats, manual includes/excludes and user-created folders. Preview-before-apply is mandatory.

## Drive v0.1 boundary

Drive is represented as a virtual filesystem over Telegram messages. The first domain model is local-only:

`DriveObject(messageId, peerId, name, mimeType, size, virtualPath)`

A virtual directory is metadata, not necessarily a Telegram channel. This prevents one-channel-per-directory scaling problems. Existing private channels may later be mounted as independent volumes.

The bootstrap does not copy code from `caamer20/Telegram-Drive`; that repository currently exposes no repository license. Its product behavior is used only as a reference.

## Build pipeline

CI performs:

1. Checkout TeleFlow bootstrap repository.
2. Checkout pinned `DrKLO/Telegram` with submodules.
3. Validate required Telegram API secrets.
4. Run TeleFlow patcher tests.
5. Apply deterministic TeleFlow overlay.
6. Verify resulting package/app identity and source anchors.
7. Build `TMessagesProj_App` `afatDebug` APK for development.
8. Upload the APK as a GitHub Actions artifact.

The first build targets upstream requirements: Android SDK 35, Build Tools 35.0.0, NDK 27.2.12479018 and JDK compatible with the upstream Gradle toolchain.

## Security and privacy constraints

- No Telegram session export.
- No hidden forwarding, hidden reads, ghost-mode or ToS-bypassing features.
- Automation is opt-in and previewable for destructive or externally visible actions.
- AI adapters are off by default and may not transmit message bodies without explicit user enablement.
- Drive encryption is not part of v0.1; it requires a separate cryptographic design and audit plan.

## Definition of done for bootstrap APK

- The patcher is covered by unit tests.
- A clean pinned Telegram checkout can be transformed deterministically.
- Product package is `com.loftfull.teleflow`.
- App name is `TeleFlow` / `TeleFlow Beta`.
- BuildVars uses user-provided API credentials and disables fork-incompatible passkeys/billing assumptions.
- TeleFlow extension manifest exists in source and reports enabled bootstrap feature flags.
- CI workflow produces an installable development APK when required secrets are configured.
